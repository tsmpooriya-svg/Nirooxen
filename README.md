# آریا صنعت — پلتفرم تجهیزات صنعتی و آبرسانی

سایت فروشگاهی-کاتالوگی فارسی (RTL) با پنل مدیریت کامل، ساخته‌شده با **Next.js 16 (App Router)**،
**TypeScript**، **Tailwind CSS v4**، **Drizzle ORM** و **PostgreSQL**.

---

## راه‌اندازی سریع

```bash
npm install                 # نصب وابستگی‌ها
cp .env.example .env        # سپس DATABASE_URL و NEXT_PUBLIC_SITE_URL را پر کنید
npm run db:migrate          # ساخت جداول
npm run db:seed             # داده نمونه (فقط محیط توسعه)
npm run dev                 # http://localhost:3000
```

**ورود به پنل (فقط محیط توسعه):** `/admin/login` — ایمیل `admin@example.com` / رمز `Admin@12345`
این حساب را `db:seed` می‌سازد و رمزش عمومی است، پس فقط برای توسعه است.
روی production از `npm run bootstrap:admin` استفاده کنید (بخش «استقرار»).

> ⚠️ `npm run db:seed` تمام جدول‌ها را TRUNCATE می‌کند و فقط برای توسعه/تست است.
> اجرای آن با `NODE_ENV=production` رد می‌شود و هیچ نوشتنی انجام نمی‌دهد.

### متغیرهای محیطی

فایل نمونه در `.env.example` است؛ `cp .env.example .env` و مقادیر را پر کنید.

| متغیر | الزامی | توضیح |
|---|---|---|
| `DATABASE_URL` | بله | رشته اتصال PostgreSQL |
| `NEXT_PUBLIC_SITE_URL` | بله در production | آدرس کامل سایت (مبنای canonical، Open Graph و sitemap). اگر در production تعریف نشود، build با خطا متوقف می‌شود تا آدرس localhost منتشر نشود. در محیط توسعه به `http://localhost:3000` برمی‌گردد. |
| `DATABASE_SSL` | خیر | اگر پایگاه داده SSL می‌خواهد، `true` |
| `DATABASE_POOL_MAX` | خیر | بیشینه اتصال‌های pool — پیش‌فرض `10` |
| `MEDIA_STORAGE_ROOT` | در production بله | ریشه ذخیره‌سازی تصاویر آپلودشده — نمونه: `/var/lib/nirooxen/media` |
| `MEDIA_MAX_UPLOAD_MB` | خیر | بیشینه حجم هر تصویر — پیش‌فرض `8` |

## ساختار پروژه

```
src/
  app/
    (site)/         صفحات عمومی — لندینگ، محصولات، برندها، اخبار، تماس…
    (admin)/admin/  پنل مدیریت — login خارج از محافظ، بقیه داخل (panel)
    api/            جستجوی سریع، خبرنامه
  components/
    ui/             کتابخانه کامپوننت پایه (دکمه، فرم، مودال، جدول، توست…)
    site/           کامپوننت‌های سایت عمومی
    admin/          کامپوننت‌های پنل
    motion/         Reveal و Counter (انیمیشن اسکرول با IntersectionObserver)
  modules/          مرز دامنه — هر ماژول queries.ts و actions.ts خودش را دارد
    catalog/  orders/  cart/  content/  admin/  auth/
  db/               schema.ts (Drizzle) + seed.ts
  lib/              auth، validation (Zod)، utils، seo، rate-limit، activity
```

**قاعده معماری:** صفحات هرگز مستقیم با `db` کار نمی‌کنند؛ همیشه از `modules/*/queries.ts`
یا `actions.ts` عبور می‌کنند. این مرز باعث می‌شود تغییر منبع داده، UI را نشکند.

## مدل فروش

- هر محصول یکی از سه حالت قیمت را دارد: **نمایش قیمت** / **استعلام قیمت** / **تماس بگیرید**
  (فیلد `priceMode`).
- دکمه محصول بر همین اساس «ثبت سفارش» یا «استعلام قیمت» می‌شود.
- ثبت فرم ⟵ رکورد در جدول `orders` ⟵ نمایش فوری در پنل مدیریت با گردش‌کار ۸ مرحله‌ای.
- **قیمت‌گذاری همیشه سمت سرور از پایگاه داده خوانده می‌شود**، نه از ورودی کاربر.

### مسیر افزودن پرداخت آنلاین (فاز بعدی)

زیرساخت از ابتدا آماده است و نیازی به بازنویسی ندارد:

1. جدول `payments` ساخته شده و منتظر اتصال درگاه است.
2. `orders` از ابتدا `paymentStatus` / `paymentMethod` / `paidAt` دارد.
3. `orderType` بین `QUOTE` و `ORDER` تمایز می‌گذارد.
4. سبد استعلام (`src/modules/cart/store.ts`) همان ساختار سبد خرید را دارد؛
   کافی است در checkout مقدار `type` را به `ORDER` تغییر دهید و پس از `createOrder`
   کاربر را به درگاه هدایت کنید.

## سئو

- `metadata` اختصاصی برای هر صفحه + `canonical`
- `sitemap.xml` و `robots.txt` پویا (`src/app/sitemap.ts` و `robots.ts`)
- داده ساختاریافته JSON-LD: Organization، WebSite، BreadcrumbList، Product، Article
- تصاویر با `next/image`، فونت‌ها self-host با `font-display: swap`
- صفحات محصول و مقاله به‌صورت ایستا (SSG) ساخته و دوره‌ای بازتولید می‌شوند

## دسترس‌پذیری

- کنتراست متن حداقل ۴.۵:۱ در هر دو تم
- `:focus-visible` روی همه عناصر تعاملی
- `prefers-reduced-motion` در سراسر سیستم حرکتی رعایت شده
- لینک «رفتن به محتوای اصلی»، برچسب ARIA روی همه دکمه‌های آیکونی
- امکان زوم تا ۵ برابر (محدود نشده)

## امنیت

- رمز عبور با bcrypt (۱۲ round)
- نشست: توکن مبهم + هش SHA-256 در پایگاه داده ⟵ امکان ابطال فوری
- کوکی `httpOnly` + `sameSite=lax` + `secure` در production
- محدودسازی نرخ روی ورود، ثبت سفارش، فرم تماس، خبرنامه و جستجوی سریع
- سقف حجم بدنه روی مسیرهای API (Server Action ها به‌صورت پیش‌فرض ۱ مگابایت محدودند)
- honeypot ضد ربات در فرم‌های عمومی
- `requireWritePermission` در **هر** Server Action (نه فقط در layout)
- پنل مدیریت با `noindex` و مسدود در `robots.txt`

## استقرار

### پیش‌نیازها

| مورد | نیاز |
|---|---|
| Node.js | خط ۲۲ (`>=22.0.0 <23.0.0`) — نسخهٔ مبنا ۲۲.۲۲.۲ در `.nvmrc` |
| npm | خط ۱۰ (`>=10.0.0 <11.0.0`) — نسخهٔ مبنا ۱۰.۹.۷ در `packageManager` |
| PostgreSQL | سازگار با ۱۶ — روی ۱۶.۱۳ آزموده شده |
| reverse proxy | الزامی؛ بخش «reverse proxy و نشانی واقعی کلاینت» |
| دامنه و TLS | خارج از این مخزن؛ وظیفه زیرساخت است |

سقف major عمدی است: ارتقای Node یا npm به خط بعدی باید یک تصمیم آگاهانه باشد،
نه چیزی که در یک محیط تازه بی‌سروصدا اتفاق بیفتد. `.npmrc` مقدار
`engine-strict=true` دارد، پس `npm ci` روی نسخهٔ ناسازگار همان‌جا شکست می‌خورد
به‌جای آنکه بعداً وسط build با خطای مبهم بایستد. `nvm use` نسخهٔ `.nvmrc` را
برمی‌دارد.

### ترتیب اجرا

```bash
npm ci
npm run preflight         # بررسی متغیرهای محیطی، بدون اتصال به پایگاه داده
npm run db:migrate        # ساخت/به‌روزرسانی جدول‌ها
npm run bootstrap:admin   # فقط یک بار: ساخت نخستین حساب مدیر
npm run build
npm start                 # پیش‌فرض روی پورت 3000
```

ترتیب مهم است: `next build` صفحه‌های محصول و مقاله را از پایگاه داده پیش‌ساخت
می‌کند، پس اگر پیش از `db:migrate` اجرا شود با خطای `relation "brands" does not
exist` متوقف می‌شود. مهاجرت‌ها پیش از بالا آمدن برنامه اجرا می‌شوند و خودِ
برنامه هنگام اجرا هیچ تغییری در schema نمی‌دهد.

`db:seed` را روی production اجرا نکنید؛ داده نمونه درج می‌کند و جدول‌ها را پاک
می‌کند. با `NODE_ENV=production` اجرای آن رد می‌شود و هیچ نوشتنی انجام نمی‌دهد.

اسکریپت‌های داده‌ای (`db:seed` · `db:push` · `db:specs` · `import-watertanks` ·
`replace-watertank-images`) از `scripts/guard-destructive.mjs` عبور می‌کنند: اگر
`NODE_ENV=production` باشد یا میزبانِ `DATABASE_URL` محلی نباشد، اجرا رد می‌شود.
خطر واقعی همین حالت دوم است — یک فایل `.env` که به پایگاه دادهٔ production اشاره
می‌کند، بدون آنکه `NODE_ENV` تنظیم شده باشد. برای اجرای آگاهانه روی میزبان
غیرمحلی: `ALLOW_DESTRUCTIVE_DB_SCRIPTS=1`. حالت `--dry`/`--dry-run` چون چیزی
نمی‌نویسد آزاد است. `db:migrate`، `db:apply` و `bootstrap:admin` عمداً محافظت
نمی‌شوند؛ اجرای آن‌ها روی production بخشی از استقرار عادی است.
پایگاه داده تازه پس از `db:migrate` هیچ کاربری ندارد، پس ساخت حساب مدیر تنها از
راه `bootstrap:admin` انجام می‌شود.

### ذخیره‌سازی تصاویر

تصاویر آپلودشده در `MEDIA_STORAGE_ROOT` نگهداری می‌شوند، نه داخل پوشه پروژه. دلیلش
ساده است: هر `npm run build` یا استقرار تازه، درخت برنامه را بازمی‌سازد و اگر
تصاویر آنجا بودند از بین می‌رفتند.

```
MEDIA_STORAGE_ROOT=/var/lib/nirooxen/media
```

الزامات:

- مسیر باید پیش از اجرا وجود داشته باشد و برای کاربر اجراکننده برنامه قابل نوشتن باشد
- باید روی فضای ذخیره‌سازی پایدار باشد
- **باید در پشتیبان‌گیری قرار بگیرد** — پایگاه داده فقط کلید فایل‌ها را دارد، نه خود آنها
- هنگام استقرار نباید پاک یا بازساخته شود

هر آپلود دو فایل تولید می‌کند:

| فایل | توضیح |
|---|---|
| `detail.webp` | نسخه تحویلی — حداکثر عرض **۱۶۰۰ پیکسل**، فرمت WebP. همان چیزی که `url` به آن اشاره دارد و ستون‌های `width`/`height` ابعادش را نگه می‌دارند. |
| `original.<ext>` | نسخه مادر، دست‌نخورده — فقط برای ساخت دوبارهٔ نسخه‌ها در آینده (مثلاً افزودن اندازه یا فرمت جدید) نگهداری می‌شود و هرگز به کاربر سرو نمی‌شود. |

در پایگاه داده هیچ مسیر مطلق فایل‌سیستمی ذخیره نمی‌شود؛ فقط یک کلید نسبی
(`storage_key`) که لایه ذخیره‌سازی آن را به نشانی عمومی ترجمه می‌کند. به همین
دلیل جابه‌جایی مسیر یا مهاجرت بعدی به Object Storage نیازی به تغییر داده محصول
ندارد.

**فایل‌های بی‌ارجاع:** بارگذاری و ذخیرهٔ محصول دو گام جدا هستند. اگر مدیر تصویری
بارگذاری کند و بعد فرم را ذخیره نکند — یا ذخیره با خطا برگردد — فایل روی دیسک
می‌ماند بدون آنکه رکوردی به آن اشاره کند. این عمدی است: پاک کردن فایل در آن لحظه،
تلاش دوباره را غیرممکن می‌کرد. پوشه‌های خالیِ به‌جامانده از حذف تصویر هم پاک
نمی‌شوند. هر دو مورد فقط فضای دیسک می‌گیرند و داده‌ای را خراب نمی‌کنند؛ در صورت
نیاز با یک کار زمان‌بندی‌شده که کلیدهای بدون رکورد در `product_images` را پاک کند
قابل جمع‌آوری‌اند. چنین کاری در این فاز نوشته نشده.

**تحویل فایل در production:** انتظار می‌رود nginx مسیر `/media/` را مستقیم از دیسک
سرو کند:

```
/media/*  →  /var/lib/nirooxen/media/*
```

برنامه یک مسیر تحویل جایگزین هم دارد تا توسعه و تست بدون nginx ممکن باشد، اما در
production نباید بار تصاویر روی Node بیفتد. پیکربندی nginx بخشی از استقرار است و
در این فاز انجام نشده.

### پشتیبان‌گیری

مخزن هیچ سازوکار پشتیبان‌گیری ندارد؛ این کار کاملاً بر عهده زیرساخت است. پیش از
انتشار، برای PostgreSQL یک پشتیبان‌گیری زمان‌بندی‌شده برقرار کنید و **بازیابی را
یک بار واقعاً آزمایش کنید**؛ پشتیبان آزمایش‌نشده پشتیبان نیست. تصاویر و فایل‌های
ایستا در همین مخزن نگهداری می‌شوند و از راه استقرار برمی‌گردند.

### ساخت نخستین حساب مدیر

```bash
npm run bootstrap:admin
```

نام، ایمیل و رمز عبور را می‌پرسد (رمز روی صفحه نمایش داده نمی‌شود). برای اجرای
غیرتعاملی می‌توانید `ADMIN_NAME` / `ADMIN_EMAIL` / `ADMIN_PASSWORD` را تعریف
کنید. رمز عبور را به‌صورت آرگومان خط فرمان ندهید؛ در تاریخچه شل باقی می‌ماند.

اسکریپت هیچ جدولی را پاک نمی‌کند و هیچ داده نمونه‌ای نمی‌سازد. اگر پایگاه داده
از قبل کاربری داشته باشد، بدون تغییر هیچ ردیفی با کد خروج غیرصفر متوقف می‌شود؛
کاربران بعدی از «پنل مدیریت › کاربران پنل» ساخته می‌شوند.

### بررسی سلامت (health check)

```
GET /api/health
```

بدون احراز هویت، فقط خواندنی، و بدون هیچ داده‌ای دربارهٔ پیکربندی یا کسب‌وکار.
پرس‌وجویش `select 1` است تا هزینه‌اش ثابت بماند.

| وضعیت | پاسخ | کد |
|---|---|---|
| برنامه و پایگاه داده سالم | `{"status":"ok","database":"ok"}` | ۲۰۰ |
| برنامه بالا، پایگاه داده در دسترس نیست | `{"status":"degraded","database":"error"}` | ۵۰۳ |

جدا بودن این دو حالت عمدی است: ۵۰۳ یعنی این instance نباید ترافیک بگیرد، در
حالی که پاسخ گرفتن اصلاً یعنی پروسهٔ Node زنده است. جزئیات خطا فقط در لاگ سرور
می‌ماند و هرگز در پاسخ نمی‌آید. برای liveness/readiness در load balancer یا
مانیتورینگ همین مسیر کافی است؛ هیچ رابط کاربری‌ای برایش وجود ندارد.

### محدودسازی نرخ در استقرار چند-instance

شمارنده‌های محدودسازی نرخ در حافظهٔ همان پروسه‌اند (`src/lib/rate-limit.ts`).
برای نصب تک‌سروری — که حالت هدف این پروژه است — درست کار می‌کند. اما اگر روزی
چند instance اجرا شد (چند process در PM2، چند کانتینر، یا مقیاس افقی)، هر
instance شمارندهٔ خودش را دارد و **سقف مؤثر در تعداد instance ها ضرب می‌شود**.
آن حالت به وضعیت مشترک (مثلاً Redis) نیاز دارد؛ تنها همین فایل باید عوض شود و
امضای `rateLimit()` تغییری نمی‌کند.

تعداد سطل‌ها سقف دارد (۲۰٬۰۰۰) چون کلید هر سطل از IP ساخته می‌شود و مهاجم
می‌تواند آن را کنترل کند؛ بدون سقف، سیلی از IP های جعلی حافظهٔ پروسه را پر
می‌کرد.

### reverse proxy و نشانی واقعی کلاینت

محدودسازی نرخ (ورود به پنل، فرم تماس، ثبت سفارش، خبرنامه و جستجو) بر پایه نشانی
IP کلاینت کار می‌کند. proxy باید هدرهای فورواردینگ را **بازنویسی** کند، نه اینکه
مقدار فرستاده‌شده توسط کلاینت را عبور دهد — در غیر این صورت مهاجم با یک هدر
ساختگی سطل محدودسازی تازه می‌گیرد:

```nginx
location / {
    proxy_pass         http://127.0.0.1:3000;
    proxy_set_header   Host              $host;
    proxy_set_header   X-Real-IP         $remote_addr;
    proxy_set_header   X-Forwarded-For   $remote_addr;
    proxy_set_header   X-Forwarded-Proto $scheme;
}
```

برنامه `X-Real-IP` را ترجیح می‌دهد و در `X-Forwarded-For` آخرین مقدار را می‌خواند
(نه اولی، که کلاینت کنترلش می‌کند). اپلیکیشن نباید مستقیم در معرض اینترنت باشد.
