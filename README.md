# آریا صنعت — پلتفرم تجهیزات صنعتی و آبرسانی

سایت فروشگاهی-کاتالوگی فارسی (RTL) با پنل مدیریت کامل، ساخته‌شده با **Next.js 16 (App Router)**،
**TypeScript**، **Tailwind CSS v4**، **Drizzle ORM** و **PostgreSQL**.

---

## راه‌اندازی سریع

```bash
npm install                 # نصب وابستگی‌ها
cp .env.example .env        # سپس DATABASE_URL و NEXT_PUBLIC_SITE_URL را پر کنید
npm run db:migrate          # ساخت جداول
npm run db:seed             # داده نمونه (فقط محیط توسعه)
npm run dev                 # http://localhost:3000
```

**ورود به پنل (فقط محیط توسعه):** `/admin/login` — ایمیل `admin@example.com` / رمز `Admin@12345`
این حساب را `db:seed` می‌سازد و رمزش عمومی است، پس فقط برای توسعه است.
روی production از `npm run bootstrap:admin` استفاده کنید (بخش «استقرار»).

> ⚠️ `npm run db:seed` تمام جدول‌ها را TRUNCATE می‌کند و فقط برای توسعه/تست است.
> اجرای آن با `NODE_ENV=production` رد می‌شود و هیچ نوشتنی انجام نمی‌دهد.

### متغیرهای محیطی

فایل نمونه در `.env.example` است؛ `cp .env.example .env` و مقادیر را پر کنید.

| متغیر | الزامی | توضیح |
|---|---|---|
| `DATABASE_URL` | بله | رشته اتصال PostgreSQL |
| `NEXT_PUBLIC_SITE_URL` | بله در production | آدرس کامل سایت (مبنای canonical، Open Graph و sitemap). اگر در production تعریف نشود، build با خطا متوقف می‌شود تا آدرس localhost منتشر نشود. در محیط توسعه به `http://localhost:3000` برمی‌گردد. |
| `DATABASE_SSL` | خیر | اگر پایگاه داده SSL می‌خواهد، `true` |
| `DATABASE_POOL_MAX` | خیر | بیشینه اتصال‌های pool — پیش‌فرض `10` |
| `MEDIA_STORAGE_ROOT` | در production بله | ریشه ذخیره‌سازی تصاویر آپلودشده — نمونه: `/var/lib/nirooxen/media` |
| `MEDIA_MAX_UPLOAD_MB` | خیر | بیشینه حجم هر تصویر — پیش‌فرض `8` |

## ساختار پروژه

```
src/
  app/
    (site)/         صفحات عمومی — لندینگ، محصولات، برندها، اخبار، تماس…
    (admin)/admin/  پنل مدیریت — login خارج از محافظ، بقیه داخل (panel)
    api/            جستجوی سریع، خبرنامه
  components/
    ui/             کتابخانه کامپوننت پایه (دکمه، فرم، مودال، جدول، توست…)
    site/           کامپوننت‌های سایت عمومی
    admin/          کامپوننت‌های پنل
    motion/         Reveal و Counter (انیمیشن اسکرول با IntersectionObserver)
  modules/          مرز دامنه — هر ماژول queries.ts و actions.ts خودش را دارد
    catalog/  orders/  cart/  content/  admin/  auth/
  db/               schema.ts (Drizzle) + seed.ts
  lib/              auth، validation (Zod)، utils، seo، rate-limit، activity
```

**قاعده معماری:** صفحات هرگز مستقیم با `db` کار نمی‌کنند؛ همیشه از `modules/*/queries.ts`
یا `actions.ts` عبور می‌کنند. این مرز باعث می‌شود تغییر منبع داده، UI را نشکند.

## مدل فروش

- هر محصول یکی از سه حالت قیمت را دارد: **نمایش قیمت** / **استعلام قیمت** / **تماس بگیرید**
  (فیلد `priceMode`).
- دکمه محصول بر همین اساس «ثبت سفارش» یا «استعلام قیمت» می‌شود.
- ثبت فرم ⟵ رکورد در جدول `orders` ⟵ نمایش فوری در پنل مدیریت با گردش‌کار ۸ مرحله‌ای.
- **قیمت‌گذاری همیشه سمت سرور از پایگاه داده خوانده می‌شود**، نه از ورودی کاربر.

### مسیر افزودن پرداخت آنلاین (فاز بعدی)

زیرساخت از ابتدا آماده است و نیازی به بازنویسی ندارد:

1. جدول `payments` ساخته شده و منتظر اتصال درگاه است.
2. `orders` از ابتدا `paymentStatus` / `paymentMethod` / `paidAt` دارد.
3. `orderType` بین `QUOTE` و `ORDER` تمایز می‌گذارد.
4. سبد استعلام (`src/modules/cart/store.ts`) همان ساختار سبد خرید را دارد؛
   کافی است در checkout مقدار `type` را به `ORDER` تغییر دهید و پس از `createOrder`
   کاربر را به درگاه هدایت کنید.

## سئو

- `metadata` اختصاصی برای هر صفحه + `canonical`
- `sitemap.xml` و `robots.txt` پویا (`src/app/sitemap.ts` و `robots.ts`)
- داده ساختاریافته JSON-LD: Organization، WebSite، BreadcrumbList، Product، Article
- تصاویر با `next/image`، فونت‌ها self-host با `font-display: swap`
- صفحات محصول و مقاله به‌صورت ایستا (SSG) ساخته و دوره‌ای بازتولید می‌شوند

## دسترس‌پذیری

- کنتراست متن حداقل ۴.۵:۱ در هر دو تم
- `:focus-visible` روی همه عناصر تعاملی
- `prefers-reduced-motion` در سراسر سیستم حرکتی رعایت شده
- لینک «رفتن به محتوای اصلی»، برچسب ARIA روی همه دکمه‌های آیکونی
- امکان زوم تا ۵ برابر (محدود نشده)

## امنیت

- رمز عبور با bcrypt (۱۲ round)
- نشست: توکن مبهم + هش SHA-256 در پایگاه داده ⟵ امکان ابطال فوری
- کوکی `httpOnly` + `sameSite=lax` + `secure` در production
- محدودسازی نرخ روی ورود، ثبت سفارش، فرم تماس، خبرنامه و جستجوی سریع
- سقف حجم بدنه روی مسیرهای API (Server Action ها به‌صورت پیش‌فرض ۱ مگابایت محدودند)
- honeypot ضد ربات در فرم‌های عمومی
- `requireWritePermission` در **هر** Server Action (نه فقط در layout)
- پنل مدیریت با `noindex` و مسدود در `robots.txt`

## استقرار

### پیش‌نیازها

| مورد | نیاز |
|---|---|
| Node.js | خط ۲۲ (`>=22.0.0 <23.0.0`) — نسخهٔ مبنا ۲۲.۲۲.۲ در `.nvmrc` |
| npm | خط ۱۰ (`>=10.0.0 <11.0.0`) — نسخهٔ مبنا ۱۰.۹.۷ در `packageManager` |
| PostgreSQL | سازگار با ۱۶ — روی ۱۶.۱۳ آزموده شده |
| reverse proxy | الزامی؛ بخش «reverse proxy و نشانی واقعی کلاینت» |
| دامنه و TLS | خارج از این مخزن؛ وظیفه زیرساخت است |

سقف major عمدی است: ارتقای Node یا npm به خط بعدی باید یک تصمیم آگاهانه باشد،
نه چیزی که در یک محیط تازه بی‌سروصدا اتفاق بیفتد. `.npmrc` مقدار
`engine-strict=true` دارد، پس `npm ci` روی نسخهٔ ناسازگار همان‌جا شکست می‌خورد
به‌جای آنکه بعداً وسط build با خطای مبهم بایستد. `nvm use` نسخهٔ `.nvmrc` را
برمی‌دارد.

### استقرار روی سرور تازه (Ubuntu 24)

فایل‌های آمادهٔ استقرار در `deploy/` هستند:

| فایل | کار |
|---|---|
| `setup-ubuntu.sh` | نصب Node 22، PostgreSQL 17، nginx، کاربر، پوشه‌ها، swap و دیوار آتش |
| `nirooxen.service` | سرویس systemd |
| `nginx-nirooxen.conf` | پروکسی و تحویل مستقیم مدیا |

```
sudo bash deploy/setup-ubuntu.sh
```

اسکریپت idempotent است و به پایگاه دادهٔ موجود دست نمی‌زند؛ در پایان گام‌های
بعدی را چاپ می‌کند.

دو نکته که عمداً در آن هست:

**PostgreSQL 17، نه ۱۶.** اوبونتو ۲۴ نسخهٔ ۱۶ دارد، ولی دامپ گرفته‌شده با ۱۷ را
`pg_restore` نسخهٔ ۱۶ باز نمی‌کند و خطایش گمراه‌کننده است. اسکریپت مخزن رسمی
PGDG را اضافه می‌کند.

**دو گیگابایت swap.** چهار گیگ رم برای اجرا کافی است، اما `next build` لحظه‌ای
بیشتر می‌خواهد و بدون swap با OOM کشته می‌شود — پیامی که ربطش به حافظه معلوم نیست.

#### تحویل مدیا در nginx

`nginx-nirooxen.conf` کل پوشهٔ مدیا را `alias` نمی‌کند، و این عمدی است. همان
فهرست سفیدی که `src/app/media/[...key]/route.ts` دارد آنجا بازتولید شده: فقط
`detail.webp` و `card.webp` عمومی‌اند و هر چیز دیگری — از جمله `original.*` که
متادیتای EXIF و مختصات GPS را نگه می‌دارد — پیش از رسیدن به دیسک ۴۰۴ می‌گیرد.

هر پیکربندی جایگزینی که کل پوشه را alias کند این سیاست را دور می‌زند.

### ترتیب اجرا

```bash
npm ci
npm run preflight         # بررسی متغیرهای محیطی، بدون اتصال به پایگاه داده
npm run db:migrate        # ساخت/به‌روزرسانی جدول‌ها
npm run bootstrap:admin   # فقط یک بار: ساخت نخستین حساب مدیر
npm run build
npm start                 # پیش‌فرض روی پورت 3000
```

ترتیب مهم است: `next build` صفحه‌های محصول و مقاله را از پایگاه داده پیش‌ساخت
می‌کند، پس اگر پیش از `db:migrate` اجرا شود با خطای `relation "brands" does not
exist` متوقف می‌شود. مهاجرت‌ها پیش از بالا آمدن برنامه اجرا می‌شوند و خودِ
برنامه هنگام اجرا هیچ تغییری در schema نمی‌دهد.

`db:seed` را روی production اجرا نکنید؛ داده نمونه درج می‌کند و جدول‌ها را پاک
می‌کند. با `NODE_ENV=production` اجرای آن رد می‌شود و هیچ نوشتنی انجام نمی‌دهد.

اسکریپت‌های داده‌ای (`db:seed` · `db:push` · `db:specs` · `import-watertanks` ·
`replace-watertank-images`) از `scripts/guard-destructive.mjs` عبور می‌کنند: اگر
`NODE_ENV=production` باشد یا میزبانِ `DATABASE_URL` محلی نباشد، اجرا رد می‌شود.
خطر واقعی همین حالت دوم است — یک فایل `.env` که به پایگاه دادهٔ production اشاره
می‌کند، بدون آنکه `NODE_ENV` تنظیم شده باشد. برای اجرای آگاهانه روی میزبان
غیرمحلی: `ALLOW_DESTRUCTIVE_DB_SCRIPTS=1`. حالت `--dry`/`--dry-run` چون چیزی
نمی‌نویسد آزاد است. `db:migrate`، `db:apply` و `bootstrap:admin` عمداً محافظت
نمی‌شوند؛ اجرای آن‌ها روی production بخشی از استقرار عادی است.
پایگاه داده تازه پس از `db:migrate` هیچ کاربری ندارد، پس ساخت حساب مدیر تنها از
راه `bootstrap:admin` انجام می‌شود.

### واردکردن کاتالوگ و تصویر محصول

کنار `import-watertanks`، چهار واردکنندهٔ دیگر داده‌های کاتالوگ را از
`scripts/data/` می‌خوانند. همه یک قرارداد دارند: یک تراکنش، تشخیص تکراری بر
اساس `slug` (محصول موجود بازنویسی نمی‌شود، فقط رد می‌شود)، درج با وضعیت
`DRAFT` تا انتشار دست انسان بماند، و `--dry` که چیزی نمی‌نویسد.

```
node scripts/import-batch1.mjs        --dry   # پمپ، منبع، ست کنترل، موتور برق
node scripts/import-fire-safety.mjs   --dry   # تجهیزات آتش‌نشانی و ایمنی
node scripts/import-photo-catalog.mjs --dry   # محصولات دارای عکس کاتالوگ سازنده
node scripts/import-rest-batch1.mjs   --dry   # باقی‌ماندهٔ دستهٔ ۱
```

قیمت فقط وقتی نوشته می‌شود که `priceMode` برابر `PUBLIC` باشد — همان قاعده‌ای که
`saveProduct` در پنل دارد. هر چهار اسکریپت از `guard-destructive.mjs` عبور
می‌کنند؛ روی سرور که `NODE_ENV=production` است، اجرای آگاهانه با
`ALLOW_DESTRUCTIVE_DB_SCRIPTS=1` انجام می‌شود و اسکریپت هشدارش را چاپ می‌کند.

نامک برند از املای لاتین ساخته می‌شود (`scripts/lib/brand-slug.mjs`) — همان
قاعده‌ای که پنل مدیریت دارد — و چکیدهٔ نام فقط وقتی به کار می‌رود که املای
لاتین نداشته باشیم یا نامکش را برند دیگری گرفته باشد. برندهایی که پیش از این
قاعده با نامک چکیده وارد شده‌اند، یک‌بار با این اسکریپت اصلاح می‌شوند:

```
node scripts/fix-brand-slugs.mjs            # پیش‌نمایش
node scripts/fix-brand-slugs.mjs --apply    # اعمال
```

فقط نامک‌هایی را دست می‌زند که دقیقاً الگوی چکیده را دارند، پس برندی که نامک
دستی دارد دست‌نخورده می‌ماند و اجرای دوباره‌اش بی‌اثر است.

#### انتشار محصولات

واردکننده‌ها محصول را `DRAFT` می‌گذارند تا انتشار تصمیم انسان بماند.
`publish-products.mjs` همان تصمیم را اجرا می‌کند. برخلاف اسکریپت‌های داده‌ای از
`guard-destructive` عبور نمی‌کند — اجرایش روی production کارِ عادی است — و
به‌جای آن پیش‌فرضش «آزمایشی» است: بدون `--apply` هیچ چیزی نوشته نمی‌شود.

```
node scripts/publish-products.mjs                      # پیش‌نمایش + گزارش کیفیت
node scripts/publish-products.mjs --apply              # انتشار همه
node scripts/publish-products.mjs --category=tanks --apply
node scripts/publish-products.mjs --with-photo --apply
node scripts/publish-products.mjs --unpublish --category=tanks --apply
```

صافی‌ها اجازه می‌دهند موجی منتشر کنید: `--category` (نامک دسته یا والدش)،
`--brand`، `--min-specs=N`، `--with-price`، `--with-photo`،
`--with-description`، `--published-since=<زمان>`، `--limit=N`.

پس از هر اجرا، دستور بازگرداندن چاپ می‌شود و همیشه `--published-since` دارد که
از خودِ پایگاه داده و داخل همان تراکنش خوانده شده است؛ پس دقیقاً همان ردیف‌ها را
برمی‌گرداند و به محصولاتی که پیش‌تر منتشر شده‌اند کاری ندارد.

پیش از نوشتن گزارش می‌دهد چند محصولِ انتخاب‌شده مشخصهٔ فنی، توضیح، برند یا عکس
واقعی ندارند — تا پیش از آنکه صفحه‌ای نیم‌بند روی سایت بیاید، ببینیدش.
`published_at` تنها بار نخست تنظیم می‌شود، پس انتشار دوبارهٔ یک محصول تاریخ
اصلی‌اش را جابه‌جا نمی‌کند.

#### زنجیرهٔ تصویر محصول

چهار ابزار که پشت سر هم عکس واقعی را از منبع تا پایگاه داده می‌برند. هیچ‌کدام
تصمیم نمی‌گیرد کدام عکس مال کدام محصول است؛ آن قضاوت با انسان است.

```
# ۱. عکس‌های جاسازی‌شده در کاتالوگ PDF سازنده را بیرون بکش
node scripts/extract-pdf-images.mjs --pdf=catalog.pdf --out=./raw

# ۲. یا: از روی فهرست «نامک،نشانی» دانلود کن (روی سیستمی که آن سایت‌ها باز است)
node scripts/fetch-product-photos.mjs --list=photos.csv --out=./raw --dry

# ۳. هر عکسی از هر منبعی را یکدست کن — سفیدسازی پس‌زمینه، برش، بوم مربع
node scripts/normalize-photos.mjs --in=./raw --out=./photos

# ۴. به محصول‌ها پیوست کن؛ نام هر فایل باید نامک محصول باشد
node scripts/import-product-photos.mjs --dir=./photos --dry
node scripts/import-product-photos.mjs --dir=./photos --replace
```

`--replace` فقط طرح‌های جانشینِ خودمان را حذف می‌کند (ردیف‌های بدون
`storage_key` که به `/images/products/…` اشاره دارند)؛ عکسی که اپراتور از پنل
بالا برده دست نمی‌خورد.

پردازش تصویر عیناً همان کاری است که پنل می‌کند: نسخهٔ تحویلی `webp` با عرض
۱۶۰۰، نسخهٔ اصلی دست‌نخورده، و همان چیدمان کلید ذخیره‌سازی.

`scripts/browser/harvest-images.js` اسکریپت سرور نیست: در کنسول مرورگر روی یک
صفحهٔ فهرست محصول اجرا می‌شود و نام و نشانی عکس‌ها را به‌صورت CSV بیرون می‌دهد
تا ورودی مرحلهٔ ۲ شود.

### ذخیره‌سازی تصاویر

تصاویر آپلودشده در `MEDIA_STORAGE_ROOT` نگهداری می‌شوند، نه داخل پوشه پروژه. دلیلش
ساده است: هر `npm run build` یا استقرار تازه، درخت برنامه را بازمی‌سازد و اگر
تصاویر آنجا بودند از بین می‌رفتند.

```
MEDIA_STORAGE_ROOT=/var/lib/nirooxen/media
```

الزامات:

- مسیر باید پیش از اجرا وجود داشته باشد و برای کاربر اجراکننده برنامه قابل نوشتن باشد
- باید روی فضای ذخیره‌سازی پایدار باشد
- **باید در پشتیبان‌گیری قرار بگیرد** — پایگاه داده فقط کلید فایل‌ها را دارد، نه خود آنها
- هنگام استقرار نباید پاک یا بازساخته شود

هر آپلود دو فایل تولید می‌کند:

| فایل | توضیح |
|---|---|
| `detail.webp` | نسخه تحویلی — حداکثر عرض **۱۶۰۰ پیکسل**، فرمت WebP. همان چیزی که `url` به آن اشاره دارد و ستون‌های `width`/`height` ابعادش را نگه می‌دارند. |
| `original.<ext>` | نسخه مادر، بایت‌به‌بایت همان فایل آپلودی — فقط برای ساخت دوبارهٔ نسخه‌ها در سمت سرور (مثلاً افزودن اندازه یا فرمت جدید) نگهداری می‌شود. **خصوصی است** و از مسیر عمومی قابل دریافت نیست. |

در پایگاه داده هیچ مسیر مطلق فایل‌سیستمی ذخیره نمی‌شود؛ فقط یک کلید نسبی
(`storage_key`) که لایه ذخیره‌سازی آن را به نشانی عمومی ترجمه می‌کند. به همین
دلیل جابه‌جایی مسیر یا مهاجرت بعدی به Object Storage نیازی به تغییر داده محصول
ندارد.

**مرز عمومی/خصوصی:** مسیر تحویل (`src/app/media/[...key]/route.ts`) فهرست
سفیدی از *نام فایل* نسخه‌های عمومی دارد — امروز `detail.webp` و جای `card.webp`
برای آینده. هر نام دیگری، از جمله `original.*`، همان ۴۰۴ فایل ناموجود را
می‌گیرد؛ پس از بیرون نمی‌توان فهمید نسخهٔ مادر وجود دارد یا نه. دلیلش این است که
نسخهٔ مادر متادیتای EXIF (از جمله GPS) و تمام رزولوشن اصلی را نگه می‌دارد، در
حالی که نسخهٔ تحویلی هنگام تولید متادیتا را دور می‌ریزد. هیچ بخشی از سایت یا پنل
مدیریت نسخهٔ مادر را از راه عمومی نمی‌خواند.

> ⚠️ **این سیاست فقط در لایهٔ Node اعمال می‌شود.** اگر nginx یا CDN کل پوشهٔ مدیا
> را با یک `alias` سرو کند، درخواست هرگز به Node نمی‌رسد و نسخهٔ مادر دوباره
> عمومی می‌شود. پیکربندی production باید همین مرز را نگه دارد: یا فقط نام‌های
> نسخهٔ عمومی را سرو کند، یا `original.*` را صریحاً رد کند. پیکربندی nginx بخشی
> از فاز استقرار است و در این مخزن وجود ندارد.

**فایل‌های بی‌ارجاع:** بارگذاری و ذخیرهٔ محصول دو گام جدا هستند. اگر مدیر تصویری
بارگذاری کند و بعد فرم را ذخیره نکند — یا ذخیره با خطا برگردد — فایل روی دیسک
می‌ماند بدون آنکه رکوردی به آن اشاره کند. این عمدی است: پاک کردن فایل در آن لحظه،
تلاش دوباره را غیرممکن می‌کرد. پوشه‌های خالیِ به‌جامانده از حذف تصویر هم پاک
نمی‌شوند. هر دو مورد فقط فضای دیسک می‌گیرند و داده‌ای را خراب نمی‌کنند؛ در صورت
نیاز با یک کار زمان‌بندی‌شده که کلیدهای بدون رکورد در `product_images` را پاک کند
قابل جمع‌آوری‌اند. چنین کاری در این فاز نوشته نشده.

**تحویل فایل در production:** انتظار می‌رود nginx مسیر `/media/` را مستقیم از دیسک
سرو کند:

```
/media/*  →  /var/lib/nirooxen/media/*
```

برنامه یک مسیر تحویل جایگزین هم دارد تا توسعه و تست بدون nginx ممکن باشد، اما در
production نباید بار تصاویر روی Node بیفتد. پیکربندی nginx بخشی از استقرار است و
در این فاز انجام نشده.

یک `alias` روی کل پوشه، مرز عمومی/خصوصیِ بالا را دور می‌زند و نسخهٔ مادر را
عمومی می‌کند. پیکربندی nginx/CDN باید همان فهرست سفید را بازتولید کند.

### پشتیبان‌گیری

`deploy/backup-nirooxen.sh` هر شب دو چیز را برمی‌دارد، چون هیچ‌کدام بدون دیگری
کامل نیست:

* **پایگاه داده** با `pg_dump --format=custom` — محصولات، سفارش‌ها، مشتریان، کاربران
* **پوشهٔ `MEDIA_STORAGE_ROOT`** به‌صورت `tar.gz` — تصاویری که از پنل آپلود شده‌اند
  و در پایگاه داده نیستند

طرح‌های پیش‌فرض محصولات (`public/images/products/`) در خود مخزن‌اند و از راه
استقرار برمی‌گردند؛ ولی هر چه از پنل آپلود شود فقط در پوشهٔ مدیا زندگی می‌کند.

```bash
sudo cp deploy/nirooxen-backup.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now nirooxen-backup.timer

sudo systemctl start nirooxen-backup.service     # اجرای دستی
journalctl -u nirooxen-backup -n 20 --no-pager   # نتیجه
systemctl list-timers nirooxen-backup            # اجرای بعدی
```

اسکریپت پس از گرفتن دامپ آن را می‌خواند و تعداد جدول‌هایش را می‌شمارد؛ اگر باز
نشد یا کمتر از حد انتظار بود، **با خطا می‌ایستد، فایل نیمه‌کاره را پاک می‌کند و
به نسخه‌های قبلی دست نمی‌زند**. چرخش نسخه‌ها فقط پس از همین تأیید انجام می‌شود،
پس یک شبِ خراب، پشتیبان‌های سالم را نمی‌برد.

متغیرها با محیط قابل تغییرند: `DB_NAME`، `BACKUP_DIR` (پیش‌فرض
`/var/backups/nirooxen`)، `MEDIA_DIR`، `KEEP_DAYS` (پیش‌فرض ۱۴)، `MIN_TABLES`.

**بازگردانی** — پوشهٔ پشتیبان فقط برای `root` خواندنی است، پس فایل با `root`
خوانده و به `pg_restore` خورانده می‌شود:

```bash
sudo -u postgres createdb nirooxen_restore
sudo runuser -u postgres -- pg_restore --dbname=nirooxen_restore \
  --no-owner --no-privileges --exit-on-error \
  < /var/backups/nirooxen/db-YYYYMMDD-HHMMSS.dump

sudo tar -xzf /var/backups/nirooxen/media-YYYYMMDD-HHMMSS.tar.gz -C /var/lib/
```

**بازیابی را یک بار واقعاً آزمایش کنید**؛ پشتیبان آزمایش‌نشده پشتیبان نیست.

#### عکس کامل، پیش از تغییر بزرگ

```bash
sudo bash deploy/snapshot-nirooxen.sh
```

**یک فایل** می‌سازد که همه‌چیز در آن است: پایگاه داده، فایل‌های آپلودشده،
`nirooxen.env`، پیکربندی nginx و systemd، و یک `MANIFEST.txt` که تاریخ، کامیت
کد، شمارش ردیف‌ها و **دستور بازگرداندن** را در خود دارد — تا اگر روزی فایل را
جدا از این مخزن پیدا کردید، هنوز بدانید با آن چه کنید.

با پشتیبان شبانه فرق دارد و جایگزینش نیست: آن یکی خودکار و دو‌فایلی است، این
یکی برای لحظه‌ای است که می‌خواهید چیزی بردارید و کنار بگذارید.

بسته پیش از اعلام موفقیت **از داخل خودش** بررسی می‌شود: دامپ از دل بستهٔ نهایی
بیرون کشیده و خوانده می‌شود و تعداد جدول‌هایش با اصل سنجیده می‌شود. بسته‌ای که
باز می‌شود ولی دامپ سالمی ندارد، پشتیبان نیست.

دو چیز عمداً داخلش نیست: **گواهی TLS** (کلید خصوصی در فایلی که روی لپ‌تاپ
جابه‌جا می‌شود ریسک است، و `certbot` در چند ثانیه دوباره صادرش می‌کند) و **کد**
(در گیت است؛ شناسهٔ کامیت در MANIFEST ثبت می‌شود، چون داده بدون کدِ هم‌نسخه
بازنمی‌گردد).

فایل خروجی رمز پایگاه داده و کلیدهای API را دارد. دسترسی‌اش ۶۰۰ گذاشته می‌شود؛
هر جا بردیدش، همان‌طور نگهش دارید.

### اعلان درخواست‌ها

درخواست تازه — چه استعلام، چه سفارش، چه پیام تماس — در پایگاه داده می‌نشیند و
تا وقتی کسی پنل را باز نکند دیده نمی‌شود. `src/lib/notify.ts` در همان لحظه یک
پیامک به شماره‌های تیم می‌فرستد.

```
SMS_PROVIDER="smsir"
SMSIR_API_KEY="…"                   # پنل sms.ir ← توسعه‌دهندگان ← کلید API
SMSIR_TEMPLATE_ORDER="…"            # شناسهٔ قالب استعلام/سفارش
SMSIR_TEMPLATE_CONTACT="…"          # شناسهٔ قالب پیام تماس
SMS_RECIPIENTS="09120000000,09130000000"
```

#### چرا قالب، و نه ارسال انبوه

نخستین پیاده‌سازی از `send/bulk` استفاده می‌کرد. سرویس پذیرفت، هزینه کم شد، و
پیامک نرسید. علتش در مستندات خود sms.ir است: خطوط انبوه به شماره‌ای که دریافت
پیامک را نزد اپراتور مسدود کرده تحویل نمی‌دهند، و در ساعات شبانه ارسال نمی‌کنند.
اعلان سفارش هیچ‌کدام را نمی‌پذیرد — باید به همان شمارهٔ تیم برسد، و ساعت سه
بامداد هم همان‌قدر مهم است که ظهر. متد **Verify** برای همین ساخته شده و هیچ‌یک
از این دو محدودیت را ندارد.

بهایش این است که متن آزاد نیست. این دو قالب را در **پنل sms.ir ← قالب‌ها**
ثبت کنید و شناسه‌شان را در تنظیمات بالا بگذارید:

```
نیروکسن
#KIND# تازه #NUMBER#
نام: #NAME#
تماس: #PHONE#
تعداد: #COUNT# قلم
```

```
نیروکسن
پیام تماس تازه
نام: #NAME#
تماس: #PHONE#
```

نام پارامترها باید عیناً همین باشد؛ `src/lib/notify.ts` با همین نام‌ها پر
می‌کند. مقدار هر پارامتر به ۲۵ نویسه بریده می‌شود، چون بریدن بهتر از رد شدنِ
کل پیامک است.

اگر قالبی تنظیم نشود ولی `SMS_LINE` تنظیم شده باشد، مسیر انبوه به‌عنوان جایگزین
به کار می‌رود و `sms:test` دربارهٔ محدودیت‌هایش هشدار می‌دهد.

```bash
npm run sms:test                 # همان مسیر ثبت سفارش، با متن آزمایشی
npm run sms:report -- <packId>   # آن ارسال رسید یا فقط پذیرفته شد؟
```

دو خبر جدا هستند و نباید یکی گرفته شوند: **پذیرش** («گرفتمش»، همان `status: 1`)
و **تحویل** («رساندمش»، که بعداً معلوم می‌شود). `sms:test` پاسخ خام را چاپ
می‌کند تا شناسهٔ پیگیری و هزینه دیده شود، و `sms:report` وضعیت تحویل همان را
می‌پرسد. `deliveryState` خالی یعنی هنوز گزارشی نیامده، نه اینکه نرسیده.

سه رفتار عمدی:

* **اگر تنظیم نشود، بی‌صدا کاری نمی‌کند.** سایت بدون پیامک کامل کار می‌کند.
* **اعلان هرگز ثبت درخواست را خراب نمی‌کند.** با `after()` پس از ارسال پاسخ به
  مشتری اجرا می‌شود، و هر خطایی بلعیده و لاگ می‌شود. قطعی سرویس پیامک نباید
  درخواستی را که همین حالا ثبت شده از بین ببرد.
* **پاسخ سرویس خوانده می‌شود، نه فقط کد HTTP.** sms.ir خطاهای دامنه‌ای —
  اعتبار تمام‌شده، خط نامعتبر، متن مسدود — را با HTTP 200 و `status` داخلی
  برمی‌گرداند؛ موفقیت یعنی `status == 1`، نه کد ۲۰۰. بدنه در هر دو مسیر خوانده
  و چاپ می‌شود، پس خطا با دلیل فارسی خودش در لاگ می‌آید نه با یک عدد تنها.

اگر در پنل sms.ir «محدودیت IP» را روشن کرده‌اید، IP سرور را همان‌جا اضافه کنید؛
وگرنه ارسال با ۴۰۳ رد می‌شود.

### قاب تصویر محصول

طرح‌های گرافیکی سایت یک تم مشترک دارند: گرادیان روشن، شبکهٔ نقشه‌کشی، و درخشش
فیروزه‌ای. همان تم پشت **عکس واقعی** محصول هم می‌نشیند، تا کاتالوگ یکدست بماند.

نکته‌ای که کل کار به آن بستگی دارد: عکس‌های استودیویی پس‌زمینهٔ سفیدِ تو‌پر
دارند، پس گذاشتن هر چیزی *پشتشان* دیده نمی‌شود. عکس با `mix-blend-mode:
multiply` روی قاب ترکیب می‌شود — ضرب در سفید یعنی «دست نزن»، پس سفید ناپدید
می‌شود و شبکه از زیرش بیرون می‌زند، بی‌آنکه لازم باشد پس‌زمینهٔ تک‌تک عکس‌ها
حذف شود.

ولی این ترفند روی عکسی که پس‌زمینه‌اش تیره است یک **مستطیل سیاه** می‌سازد — و
در همان نمونهٔ نه‌تایی کاتالوگ، یکی چنین بود. پس هر تصویر یک وضعیت دارد، در ستون
`product_images.backdrop`:

| مقدار | یعنی |
|---|---|
| `cut` | پس‌زمینه هنگام آپلود برداشته شده؛ تصویر شفاف است |
| `light` | برداشته نشد ولی روشن است؛ با `multiply` پنهان می‌شود |
| `dark` | هیچ‌کدام؛ تصویر همان‌طور که هست نمایش داده می‌شود |
| تهی | بررسی نشده — همان `dark` رفتار می‌کند، که حالت امن است |

#### برداشتن پس‌زمینه هنگام آپلود

`src/lib/media/cutout.ts` پس‌زمینه را با **پرکردن سیلابی از لبه** برمی‌دارد، نه
با قاعدهٔ «هر پیکسل سفید را شفاف کن». تفاوت تعیین‌کننده است: برچسب سفید روی بدنهٔ
پمپ یا بازتاب نور روی فلز به لبهٔ تصویر وصل نیست، پس دست‌نخورده می‌ماند؛ قاعدهٔ
رنگی ساده وسط محصول سوراخ می‌کرد.

سه نرده‌بان دارد و اگر هرکدام رد شود، تصویر **دست‌نخورده** می‌ماند — تصویر بریدهٔ
بد از تصویر نبریده بدتر است:

* لبهٔ تصویر باید یکدست باشد (عکس استودیویی، نه عکسِ داخل انبار).
* اگر تقریباً همه‌چیز برداشته شد، محصول هم‌رنگ پس‌زمینه بوده.
* اگر تقریباً هیچ برداشته نشد، حاشیه‌ای نبوده.

خروجی WebP با کانال شفافیت است و تقریباً هم‌اندازهٔ نسخهٔ قبلی درمی‌آید. **نسخهٔ
اصلی هیچ‌وقت تغییر نمی‌کند**، پس اگر روزی روش بهتری آمد می‌شود از روی همان
دوباره ساخت.

#### تصویرهای قدیمی

`npm run db:backdrops:dry` و بعد `npm run db:backdrops` — فقط دسته‌بندی می‌کند و
فایلی را تغییر نمی‌دهد. ملاکش **سهمِ روشن در حلقهٔ لبه** است نه میانگین آن؛
محصول تیره‌ای که تا لبه ادامه دارد میانگین را پایین می‌کشد در حالی که پس‌زمینه
هنوز سفید است.

#### تم تیره

تصویر `cut` روی هر زمینه‌ای می‌نشیند، پس در تم تیره قاب هم واقعاً تیره می‌شود.
تصویر `light` این آزادی را ندارد — `multiply` روی زمینهٔ تیره کل عکس را سیاه
می‌کند — و قاب روشن خودش را نگه می‌دارد. تا وقتی هر دو نوع در کاتالوگ باشند،
یک صفحه می‌تواند قاب روشن و تیره را کنار هم نشان بدهد؛ با آپلود شدن عکس‌های
واقعی، همه‌چیز به سمت `cut` می‌رود.

طرح‌های SVG دست‌نخورده می‌مانند: قاب خودشان را درون فایل دارند و ترکیب دوبارهٔ
دو شبکهٔ ۲۴ پیکسلیِ ناهم‌تراز فقط آشفتگی می‌ساخت.


ده آزمون، حدود بیست ثانیه. جای بازبینی دستی پیش از انتشار را می‌گیرند: سلامت
سرویس و پایگاه داده، بالا آمدن صفحهٔ اصلی با دسته‌بندی‌ها، رفتن از فهرست به
صفحهٔ محصول، جست‌وجو، **ثبت استعلام تا گرفتن شمارهٔ درخواست**، فرم تماس، رد شدن
رمز اشتباه، ورود با رمز درست، بسته بودن پنل بدون ورود، و ۴۰۴ به‌جای خطای سرور.

عمداً کم‌اند. مجموعه‌ای که چند دقیقه طول بکشد کسی اجرا نمی‌کند، و آزمونی که
اجرا نشود از نبودنش بدتر است چون اطمینان کاذب می‌دهد.

سه نکتهٔ عملی:

* **فقط روی پایگاه دادهٔ محلی اجرا می‌شوند.** آزمونِ استعلام واقعاً یک سفارش
  می‌نویسد، پس همان محافظِ اسکریپت‌های داده‌ای اینجا هم هست — یک بار پیش از
  بالا آمدن سرور و یک بار پیش از خود آزمون‌ها.
* **ورود محدودکنندهٔ نرخ دارد** و هر تلاش شمرده می‌شود، نه فقط ناموفق‌ها: هشت
  بار در پانزده دقیقه. چند اجرای پشت‌سرهم روی یک سرورِ در حال اجرا به سقف
  می‌خورد؛ آزمون آن حالت را تشخیص می‌دهد و به‌جای قرمز شدن، رد می‌شود. سرور را
  تازه کنید تا شمارنده صفر شود.
* اگر محیط مرورگر از پیش نصب‌شده دارد، مسیرش را در `PLAYWRIGHT_CHROMIUM_PATH`
  بگذارید. روی ماشین معمولی یک بار `npx playwright install` کافی است.

### آمار بازدید

**پنل › آمار بازدید.** از داده‌های خود سایت، بدون سرویس بیرونی و بدون کوکی —
که در ایران مزیت عملی هم دارد: سرویس خارجی یا کند است یا در دسترس نیست.

چهار چیز را جواب می‌دهد: چند نفر آمدند، روند چطور بوده، چه صفحه‌هایی را دیدند،
و از کجا آمدند. بازه‌های ۷، ۳۰ و ۹۰ روز.

دو تصمیم که عمدی‌اند و نباید بی‌خبر عوض شوند:

* **IP ذخیره نمی‌شود.** ستون `visitor` یک درهم کوتاه از IP و مرورگر است با نمکی
  که هر روز عوض می‌شود و جایی صادر نمی‌شود. یعنی «چند نفر امروز» قابل شمارش است
  و دنبال‌کردن یک نفر در طول زمان نیست. به همین دلیل جمعِ بازدیدکنندگان روزها با
  تعداد یکتای کل بازه برابر نیست — کسی که دو روز آمده دو بار شمرده می‌شود.
* **از ارجاع‌دهنده فقط دامنه.** نشانی کامل می‌تواند عبارت جست‌وجو یا شناسهٔ کارزار
  را با خود بیاورد؛ برای «از کجا می‌آیند» دامنه کافی است.

ثبت از سمت مرورگر انجام می‌شود (`/api/view`)، نه از میان‌افزار: میان‌افزار
prefetch و خزنده را هم می‌شمارد، و در App Router جابه‌جایی‌های داخلی اصلاً به
سرور نمی‌رسند. مسیرهای `/admin`، `/api` و `/media` و عامل‌های کاربری رباتی شمرده
نمی‌شوند.

رنگ دو سری نمودار در `globals.css` توکن‌های `--chart-*` هستند و با اسکریپت
سنجیده شده‌اند (باند روشنایی، کف اشباع، جدایی در سه نوع کوررنگی، کنتراست با
زمینه) — در هر دو حالت روشن و تیره. اگر عوضشان کردید، دوباره بسنجید.

### آمار جست‌وجو

هر جست‌وجو در `search_queries` ثبت می‌شود: عبارت پس از یکسان‌سازی، تعداد نتایج،
و اینکه از جست‌وجوی سریع آمده یا از صافی صفحهٔ محصولات. هیچ چیزی که کاربر را
شناسایی کند ذخیره نمی‌شود — نه IP، نه نشست.

گزارشش در **پنل › لاگ فعالیت‌ها** است، دو فهرست: پرجست‌وجوترین عبارت‌ها، و
عبارت‌هایی که هیچ نتیجه‌ای نداشته‌اند. دومی مهم‌تر است — هر ردیفش یا کالایی است
که ندارید، یا کالایی که دارید و نامش با زبان مشتری نمی‌خواند.

### ساخت نخستین حساب مدیر

```bash
npm run bootstrap:admin
```

نام، ایمیل و رمز عبور را می‌پرسد (رمز روی صفحه نمایش داده نمی‌شود). برای اجرای
غیرتعاملی می‌توانید `ADMIN_NAME` / `ADMIN_EMAIL` / `ADMIN_PASSWORD` را تعریف
کنید. رمز عبور را به‌صورت آرگومان خط فرمان ندهید؛ در تاریخچه شل باقی می‌ماند.

اسکریپت هیچ جدولی را پاک نمی‌کند و هیچ داده نمونه‌ای نمی‌سازد. اگر پایگاه داده
از قبل کاربری داشته باشد، بدون تغییر هیچ ردیفی با کد خروج غیرصفر متوقف می‌شود؛
کاربران بعدی از «پنل مدیریت › کاربران پنل» ساخته می‌شوند.

### بررسی سلامت (health check)

```
GET /api/health
```

بدون احراز هویت، فقط خواندنی، و بدون هیچ داده‌ای دربارهٔ پیکربندی یا کسب‌وکار.
پرس‌وجویش `select 1` است تا هزینه‌اش ثابت بماند.

| وضعیت | پاسخ | کد |
|---|---|---|
| برنامه و پایگاه داده سالم | `{"status":"ok","database":"ok"}` | ۲۰۰ |
| برنامه بالا، پایگاه داده در دسترس نیست | `{"status":"degraded","database":"error"}` | ۵۰۳ |

جدا بودن این دو حالت عمدی است: ۵۰۳ یعنی این instance نباید ترافیک بگیرد، در
حالی که پاسخ گرفتن اصلاً یعنی پروسهٔ Node زنده است. جزئیات خطا فقط در لاگ سرور
می‌ماند و هرگز در پاسخ نمی‌آید. برای liveness/readiness در load balancer یا
مانیتورینگ همین مسیر کافی است؛ هیچ رابط کاربری‌ای برایش وجود ندارد.

### محدودسازی نرخ در استقرار چند-instance

شمارنده‌های محدودسازی نرخ در حافظهٔ همان پروسه‌اند (`src/lib/rate-limit.ts`).
برای نصب تک‌سروری — که حالت هدف این پروژه است — درست کار می‌کند. اما اگر روزی
چند instance اجرا شد (چند process در PM2، چند کانتینر، یا مقیاس افقی)، هر
instance شمارندهٔ خودش را دارد و **سقف مؤثر در تعداد instance ها ضرب می‌شود**.
آن حالت به وضعیت مشترک (مثلاً Redis) نیاز دارد؛ تنها همین فایل باید عوض شود و
امضای `rateLimit()` تغییری نمی‌کند.

تعداد سطل‌ها سقف دارد (۲۰٬۰۰۰) چون کلید هر سطل از IP ساخته می‌شود و مهاجم
می‌تواند آن را کنترل کند؛ بدون سقف، سیلی از IP های جعلی حافظهٔ پروسه را پر
می‌کرد.

### reverse proxy و نشانی واقعی کلاینت

محدودسازی نرخ (ورود به پنل، فرم تماس، ثبت سفارش، خبرنامه و جستجو) بر پایه نشانی
IP کلاینت کار می‌کند. proxy باید هدرهای فورواردینگ را **بازنویسی** کند، نه اینکه
مقدار فرستاده‌شده توسط کلاینت را عبور دهد — در غیر این صورت مهاجم با یک هدر
ساختگی سطل محدودسازی تازه می‌گیرد:

```nginx
location / {
    proxy_pass         http://127.0.0.1:3000;
    proxy_set_header   Host              $host;
    proxy_set_header   X-Real-IP         $remote_addr;
    proxy_set_header   X-Forwarded-For   $remote_addr;
    proxy_set_header   X-Forwarded-Proto $scheme;
}
```

برنامه `X-Real-IP` را ترجیح می‌دهد و در `X-Forwarded-For` آخرین مقدار را می‌خواند
(نه اولی، که کلاینت کنترلش می‌کند). اپلیکیشن نباید مستقیم در معرض اینترنت باشد.
